Its static pages are structurally suitable for web hosting, but the current repository is **not an attached Manus WebDev project** in this session. The safe path is to keep the approved site content and design, create or attach the appropriate Manus WebDev project, and migrate the contact submission to a Manus-supported server-side route or another approved secure form service before connecting the domain. Do not expose an email credential in browser JavaScript. Do not create a replacement form until the chosen Manus backend architecture, recipient handling, storage policy, and notification path are confirmed.

Its current domain flow is managed from Manus Settings/Data controls, and the exact DNS target values are generated by Manus for the specific deployed website. DNS must not be changed from this task. ## C. Custom-domain setup

Manus documents custom-domain support for paid users. The documented flow is to open Manus Settings, use the Data controls domain management area, select or connect the domain, and follow the generated instructions. For an existing external domain, use the existing-domain connection flow. Manus specifically warns that the `www` subdomain may need a separate DNS record and recommends selecting the option to set up both root and `www` when available. If the connection reports that the `www` certificate has not been provisioned, the documented remedy is to disconnect and reconnect the domain using the external-domain flow and select “Set up both.” [1]

The exact record type and value must come from the Manus domain-management screen for the deployed project. Do not invent an A record or CNAME target. Manus also documents a path for adding specific DNS records through Settings/Data controls, including MX, CNAME, and TXT records. That capability does not authorize replacing existing mail records.

Manus’s documented domain flow provisions or coordinates TLS for the connected domain, but certificate issuance must be verified after connection. Do not direct production traffic to the new host until both `https://openv.co.za/` and `https://www.openv.co.za/` have valid certificates, serve the intended deployment, and redirect consistently.

## I. Post-launch checklist

After DNS propagation, check both root and `www` over HTTP and HTTPS. Confirm the intended `www` canonical redirect, valid TLS certificates, correct page content, no mixed-content warnings, and correct `robots.txt` and sitemap URLs. Check the homepage, Team, Manage, Connect, Secure, Grow, thank-you, contact-error, PAIA, Whistleblower, and Terms routes.

Test desktop and mobile navigation, keyboard operation, Services submenu behavior, FAQ disclosure, every primary CTA, footer links, form success/failure handling, reduced-motion behavior, hero poster fallback, and remote video playback. Inspect the browser console and network panel for missing CSS, JavaScript, fonts, images, or video resources.

Verify that mail still flows through the existing MX provider. Confirm SPF, DKIM, and DMARC records remain present. If the form uses a Manus server route, verify validation, rate limiting or abuse protection, storage policy, notification delivery, and access permissions. Do not treat a successful HTTP response as proof that an email was delivered.

Submit the final sitemap to the correct search-console property only after the custom-domain deployment serves the intended canonical pages. Monitor DNS, TLS, form, mail, and crawl errors during the first propagation window.
